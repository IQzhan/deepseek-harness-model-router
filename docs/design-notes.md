# DSH 任务路由 + 全局负载均衡：配置方案

让 DSH **按任务语义**调用指定模型：主模型执行过程中由系统判定"这一轮在做什么"，
再从该任务的**模型池**里按权重选一个模型；池内多个模型**全局均衡**，不是每个会话各自轮转。
配置入口在 **设置 → 任务路由**，与 General / Models / Plugins 同级。
池里的可选模型来自**实时模型目录**，所以模型列表里有的都能配。

---

## 1. 一句话说清分层

```
预设 (preset)  ──授权──►  任务 (task)  ──按权重铺开──►  模型池 (pool)
   谁能用                   做什么                          用哪些模型
```

三层各管一件事，这是整个设计解耦的地方：

| 层 | 归谁 | 改它会影响 |
| --- | --- | --- |
| **任务库 / 模型池** | 全局唯一 | 所有已授权预设 |
| **预设授权** | 每个预设一份 | 只影响该预设 |
| **路由决策 / 轮转状态** | 进程唯一 | 全部会话共享 |

**任务和模型池是全局的，权限是按预设的。** 预设永远不重新定义任务——
所以新增一个任务只需要配一次，所有预设立刻可选。

## 2. 判定链路：四级阶梯

每一轮请求按顺序过四级，先命中先赢：

| 级别 | 依据 | 代价 | 例子 |
| --- | --- | --- | --- |
| 1 | 显式指令 `[task: web-search]` | 零 | 用户在消息里点名 |
| 2 | 技能 / 关键词 / 工具表 | 零 | `[skill: diy-freecad]`、命中"建模"、请求声明了某工具 |
| 3 | **语义分类**（独立模型调用） | 一次廉价调用/轮 | "把这个零件做出来" |
| 4 | 默认任务 | 零 | 都没命中时兜底 |

**为什么第 3 级才是"大模型自己判断"。** 前两级免费且精确——用户已经明说了，
再花一次模型调用去重新发现一遍是浪费。真正需要语义判断的，是那些关键词覆盖不到的
"任意不确定的任务"，所以分类器只在第 3 级出场。

**分类器怎么工作**

- 把每个任务的 `description` 拼成候选清单，连同最近几轮对话发给一个**你指定的廉价模型**；
- 要求只回一个任务 id（或 `none`）；
- 结果**每轮缓存一次**，一轮内的多个 step 不会重复分类；
- 分类模型、超时都可配，**分类失败不影响对话**——退回默认任务继续。

它是一次**普通嵌套调用**（走 `llm.stream`，不是 `agent/request`），所以不会递归回路由；
路由也是显式指定的，别的机制动不了它。

**输入有多大？为什么给的是 token 上限而不是字数上限**

分类器读到的内容 = 子会话的**开场指令**（它被派出来时的那句话，信号最强）+ **最近几轮**的
对话尾巴，然后整体裁到 `classifier.maxInputTokens`。候选清单每个任务只占一行。

- 实测量级：上面那套配置一次判定 **20–30 tokens 输入**，回复 1 个单词。所谓"32K 以内"
  远远够用，正常情况连零头都用不到；
- 预算按 **token** 算，不按字符——同样 4000 字符，英文约 1000 token，中文约 4000 token，
  字符上限给不出任何保证；
- 裁剪按文本自身的字符/token 比例推算，并且**循环收紧直到估算值真的不超预算**，
  所以"不超上限"是构造出来的事实，不是名义承诺；
- 长文本先留**开头 60%**、再补尾巴：判断"这是哪类任务"靠的是开场的任务描述，
  不是最后一个工具输出。

> 上游 provider 的连通性不属于本插件：池子里指向一个连不上的 host，请求就会以网络错误失败
> （`UND_ERR_CONNECT_TIMEOUT` 之类）。配池子前确认该 provider 真能连通，别只看它出现在目录里。

**分类器是什么形态、可靠性怎么保证**

它**不是一个会话，也不是一个子智能体**：没有 session、没有历史、没有工具，就是 Host 进程里
一次普通的嵌套 `llm.stream()` 调用（`purpose: 'model-routing-classify'`）。每次判定都是独立的
一次性请求，判定完即结束，两次判定之间不保留任何状态。所以它**不需要长期监控**，也没有
"分类器会话"这种东西可管。

可靠性靠四条，全部是构造出来的，不依赖模型自觉：

| 措施 | 说明 |
| --- | --- |
| 输入有界 | 开场指令 + 最近 4 条消息，裁到 `maxInputTokens`；prompt 每个候选任务只加一行 |
| 输出预算 256 | **不是 16**。思考型模型把 reasoning 算进输出预算，16 会让它把额度全花在推理上、一个字都不回——实测就是这个现象，而空回复只能被读成"没答" |
| 失败重试一次 | 回复不可用时再问一次（免费聚合路由的下游是随机的：实测 12 次里有 1 次回了安全分类器的字符串 `User Safety: safe`，另一次回 400 "Reasoning is mandatory"）。**但只重试"快速失败"**：已经耗掉一半预算的慢失败直接放弃——重试不能把卡顿翻倍 |
| 结果每轮缓存 | `(sessionId, turn)` 只判定一次；失败也缓存，不会反复烧 token |
| 兜底永不失败 | 超时/限流/胡言乱语 → 落到默认任务；没有默认任务 → 保持子智能体继承的模型。**判定失败绝不会让这一轮对话失败** |

"会不会浪费 token"：只有**确定性规则全部没命中、且分类器已启用**时才会调用；一次判定实测输入
**20–30 tokens**，输出一个 id（约 1–5 tokens）。确定性命中（关键词、工具名、显式 `[task: …]`）
时**一次都不调**。关掉分类器就是零成本，且没有任何后台开销。

> **想要最可靠，就别把分类器指给"聚合路由"**：`openrouter/free` 这类模型每次挑不同的下游，
> 行为不稳定。钉住一个便宜且稳定的具体模型会好得多。上面 12/12 是**加了重试之后**的结果；
> 同一组用例在加重试之前是 8/12。

## 3. 全局均衡：状态放在哪，不放在哪

这是需求里最关键的一条：**"插件全局进行负载均衡规划分配（不是每个对话单独）"**。

```
rotations: taskId -> 权重向量       ← 全局，所有会话共享，永不按会话分片
pins:      (sessionId, turn) -> 模型 ← 只用来保证"一轮内不换模型"，带 TTL
```

- **轮转状态只有一份**（每个任务一个向量）。十个会话跑同一个任务，会按配置的比例
  落在池内模型上，而不是各自从第一个模型开始。
- **轮内一致**按"轮"钉住：一轮选定后，该轮所有 step 复用同一模型——
  保住 prompt 前缀缓存，也避免一次工具调用就换了"说话的人"。
- 钉住是**旁挂**的，不是轮转的一部分：清掉它不影响全局配比。

算法用 **smooth weighted round-robin**（nginx 那套）。取模会输出 `a a b`（比例对，看着很顿），
smooth WRR 输出 `a b a`——这才是"均衡"该有的样子。

**权重配置**：池里每个模型一个正整数权重，`2 : 1` 就是每 3 轮里 2 次、1 次。

**`reasoningEffort`（每个任务可选）**：路由改写 provider/model 时，继承来的 reasoning effort 会被
丢掉，于是适配器落回**路由自己的默认值**——廉价池因此可能每步都在付 `high` 的推理成本（实测：
`openrouter/free` 的子会话出现过 2 次空回复重试）。给任务写 `reasoningEffort: low` 就能把它压下来；
不写就保持现状（路由默认）。

**声明了就必须落地：强度是"就近映射"的，不是照抄也不是丢弃。** DSH 会拿模型能力校验请求，
并且**明确拒绝夹取**（`llm` 源码原话："no clamping or aliasing is performed"）：模型没有的档位
直接抛 `UNSUPPORTED_REASONING_EFFORT`，一个 token 都不会产出（实测：b-ai 的 `qwen3.8-flash`
遇到 `max` 当场终止子会话）。于是"给任务写了 `low`"曾经只有两种结局，而两种都不对：

| 结局 | 什么时候发生 | 问题 |
| --- | --- | --- |
| 原样发出去 | 模型不支持这一档 | 整轮直接死掉 |
| 悄悄丢掉 | 路由换了模型（**常态**） | 你以为在省钱，其实在付模型默认档（常常是 `high`） |

现在的规则：用 `llm.resolveModelInfo()` 问一次目标模型有哪些档位（**按路由缓存**，异步、只在首次
付出一次代价），然后

1. 声明值在支持列表里 → **原样保留**（精确优先）；
2. 不在 → 沿 `max → high → medium → low → off` **向下**找最近的（省钱是声明的动机，多要一点是
   账单，少要一点只是四舍五入）；
3. 连最低档都比声明高 → 取**模型自己的最低档**（比丢掉键、把决定权交给模型默认值更贴近"尽量少想"）；
4. 不支持任何档位（`reasoning` 块缺失）→ **删掉这个键**（这正是那两起真实故障）；
5. 问不到（老版本 `llm` 没有这个方法，或查询失败）→ **照声明原样发**，由适配器报真实的错，
   而不是插件悄悄不听话。

能力探测结果按 `provider/model` 缓存（上限 64 条，超了整体清空），所以热路径上不会每次请求都去问
适配器。

**子智能体的预设与提示词（`childPersona` / `childTools`，都可选）**

子智能体**没有自己的预设**：委派路径里 `agentPresets.composeFrom(childCtx, parent.ctx)` 把子作用域
绑到**父的 standing mount** 上（`agent-presets/src/mount.ts:243-251`），所以子会话跑的就是父的预设，
全量继承。于是：

| 影响 | 事实 |
| --- | --- |
| 提示词 | 若父预设的 persona 是 `complete: true`（`diy-smart` 就是），子会话的 system prompt **就是那几行**，其它 section 全被抑制 → 提示词层面几乎零继承成本 |
| 提示词（非 complete 预设） | 父预设的**每个**提示段都会继承过去（plan/workflow/goal 指引…）→ 真正的浪费与心智干扰 |
| **工具表** | 无论哪种预设都全量继承：子会话拿到全部工具（含 JSON schema，每次请求都发）。这是每步都付的 token，且与它的任务无关 → 分散注意力 |
| runtime context | `includeRuntimeContext: false` 的作用域抑制对子会话同样生效 |

所以要"专用精炼"，控制的是**这两件事**：

```yaml
- id: web-search
  childPersona: |-
    You are the executor for one look-up. Answer from sources you actually opened, and cite them.
  childTools:
    allow: [web_search, web_fetch, read, write]   # 或 deny: [...]
```

- `childPersona`：在**子作用域**用 `deployment:persona-prefix` 同名注册并带 `complete: true`。
  作用域链按名字合并、近者胜（`system-prompt/src/index.ts:569`，且被遮蔽的文本提供者**不会被执行**），
  所以它**整体替换**父的定义，且全链只剩一个 complete 段 —— 子会话的 system prompt **正好是这段文本**。
- `childTools`：作为 `toolFilter` 随创建请求下发，provider 在**建子会话之前**校验并应用
  （未知工具名当场失败，且不会留下孤儿会话）。
- **两个都不写 = 完全继承**（默认行为不变）。

> **不推荐"每个任务一个预设"**：委派路径没有"子会话用哪个预设"的参数（换预设要走异步
> `recompose`，与子会话第一次请求存在竞态），而且 N 个任务 = N 个预设文件，直接破坏零配置入侵。
> 上面两个字段是等价且更简的表达。

**套娃（子智能体再细分）只由 `childDelegation` 决定，与预设无关**：

| `childDelegation` | 子会话的委派工具 | 深度预算 | 强制点 |
| --- | --- | --- | --- |
| `false`（默认） | 外部**屏蔽不掉**（见下）；继承来的委派名会被 `restrict` 掉，子会话自己预设注册的那一份屏蔽不掉 | 深度 `< 1` 才允许委派 | `ctx.subagents` 上的深度守卫（所有委派路径的必经点） |
| `true` | 同上 | 深度 `< 2` 才允许委派（只多一层） | 同上，预算读到的是实时配置 |

**这里必须说清一件事，因为文档曾经说错过。** 早期版本写的是"子作用域把所有委派工具名
`restrict` 掉，所以即使预设自带 `subagent` 行，子会话也看不见它"。**实测证明这是错的**：

- 子会话自己跑的就是父的预设，`composeFrom` 会把 preset 的委派行**装进子会话自己的作用域**；
- 作用域**自有层**注册的名字，外部 `restrict` 是拒绝的（"unknown global tool"）——而且一旦
  过滤器里出现这个名字，**整个过滤器都会被丢掉**（连任务声明的 `deny` 一起失效）；
- 白名单同样挡不住它：实测子会话工具表从 33 → 32（继承了 `send_message`/`list_agents` 被移除），
  `subagent` 仍在。

代价是实测出来的：`childDelegation: false` 时，子会话调用 `subagent` **真的创建出了一个
`delegationDepth: 2` 的孙子会话**。`maxDepth` 只管得住本插件自己发出的启动请求，管不住内置工具。

所以深度策略下沉到 `ctx.subagents`：包住 `start` 与 `startContinuable`，凡是调用者
`delegationDepth >= 预算` 的委派一律拒绝（错误文案与插件自己的工具一致）。它装在**服务实例**
上、随 fiber 撤销、可被**关闭**（`enabled: false` 时不留痕迹）；装不上（例如服务被冻结）会记进
`errors[]`，并在 `/health` 的 `delegation.depthGuard` 上显示为"未生效"——护栏悄悄不在，比没有护栏更糟。

### 失败升级链

请求失败时（429/5xx）监听 `agent/request-error`，按**三级**处理，逐级降级，绝不空转：

| 情况 | 处理 |
| --- | --- |
| 池里还有没试过的模型 | 轮转到**下一个候选**并 `{ kind: 'retry' }` |
| 整个池都失败了 | 把该任务**本轮拉黑**，改用**默认任务**重试 |
| 默认任务也失败 / 没有默认任务 | **不再改写路由**，不返回 retry——失败如实上抛给调用方，由它自己继续干活 |

两个容易踩空的细节：

- 转的是**哪个任务**，由一个 `(sessionId, turn) -> taskId` 的记录决定：选定路由时就记下来，
  失败时照着转。早先的写法是从轮转计数里反推"哪个池看起来最忙"，一旦一个会话用过不止一个任务，
  转的就不是失败的那个池——错得安静，还白烧一次重试。
- **只 `rotate()` 是不够的**：重试自己那次 `next()` 会消耗掉旋转之后的下一个槽位，于是又落回
  刚失败的那个模型。必须 `rotateTo()` 拿到"转到了谁"，再用 `pin()` 把它钉给这一轮。
  这个 bug 是加了新测试才暴露出来的（旧测试只断言了日志，没断言落点）。

被拉黑的任务在一轮内不会再被选中——包括关键词命中的情况，否则重试会直接解析回同一个池。

## 4. 权限规则（谁会被路由）

| 条件 | 结果 |
| --- | --- |
| **不是子智能体会话** | **完全不动** —— 主对话永远用你在输入框旁选的模型 |
| 总开关关闭 | 完全不动 |
| 预设未授权 | 完全不动（**默认状态，装插件不改变任何现有行为**） |
| 预设授权为"仅限指定任务" | 只用列表内的任务 |
| 是子智能体、且命中任务 | 用该任务的模型池 |
| 是子智能体、未命中、有可用默认任务 | 用默认任务 |
| 是子智能体、未命中、无默认任务 | 保持它继承的模型 |

**范围只有一种：被委派出去的会话。** 主智能体（以及主智能体自己的每一轮）不受任何影响——
它的模型、工具表、上下文都没被改动过，所以路由出错的代价最多是一个子任务，
不会污染你正在进行的对话。子智能体再往下委派的孩子同样在这个范围内。

> 「尊重手动选择」和「路由子智能体」两个开关已删除。
> 前者在主对话不再被路由之后就没有意义了；后者改为默认行为——插件本来就只管子智能体。

> 默认任务是一个**引用**（`defaultTaskId`），不是任务上的勾选标记。
> 一个标着"我是默认"却模型池为空的任务，在使用点上看和"根本没有默认"无法区分；
> 引用则天然只有两种结果：解析到能服务的任务，或者等于没有。
> 引用指向的任务被停用、池为空、或 id 不存在时，一律等同于**没有默认任务**。

## 4.5 委派能力由本插件提供（不改任何预设文件）

这是"主智能体从不派子智能体"的根治办法。`diy-smart` 里**根本没有 delegation 行**，
所以主智能体连 `subagent` 工具都没有——不是它不想派，是没有工具可派。

本插件在**运行时**把这件事接管过来，一个字都不写进预设：

| 动作 | 机制 |
| --- | --- |
| 提供委派工具 | 在**每个被授权预设的 agent 作用域**里注册本插件自己的 `subagent` 工具（`agent.ctx.plugin({inject:['tools']})`） |
| 优先级高于内置 | 同名注册**遮蔽**继承来的内置 `subagent`（已用真实 `ToolRuntime` 验证：`get()` 返回的是我们的定义） |
| 屏蔽内置 | 对作用域内**实际存在**的内置委派工具名调用 `restrict({deny:[…]})`；`restrict` 对未知名字会直接报错，所以逐个 try/catch 探测，不存在就等于无需屏蔽（挡不住的名单会记进 `/health` 的 `agents[].unmasked`，不假装成功） |
| 撤销授权 | 销毁那个 fiber 即可——工具消失、遮蔽解除、内置定义原样回来。**没有任何配置文件被改动过**，所以不存在"还原时覆盖了你后来的修改"这种风险 |
| 子智能体不再分发 | 工具**只装给非子智能体**；此外在 `ctx.subagents` 上设深度守卫（`childDelegation` 决定预算是 1 还是 2），并且工具在 `execute` 里也拒绝子智能体调用（多重保险，但**真正生效的是服务上的守卫**——见上） |

**"撤销即还原"的成立条件是：fiber 从被创建的那一刻就被记住。** Cordis 异步启动插件，
`ctx.plugin()` 返回时 `apply` 还没跑，所以"启动成功才登记"这种写法会把一个**已经在工作的**
安装丢掉——工具还在、令牌还在用，却没有句柄能 dispose 它，撤授权也就撤不干净（详见 5.2.2(d)）。
现在的规则是：fiber 先登记，`applied` 单独记录启动是否跑过；启动期抛错就地 teardown + 上报。

**提示词注入走工具描述，不走提示段。** 这是被预设结构逼出来的选择：`diy-smart` 的 persona 是
`complete: true` + `includeRuntimeContext: false`，`packages/core/system-prompt/src/index.ts:590-625`
会把**所有**其它 section 抑制成一个，并把 contexts 清空。工具定义不是 prompt section，
无论 persona 怎么设都能到达模型。所以任务清单、委派规则、"子智能体是执行者"这些全部写在
工具描述里，配置页加一个任务，描述自动跟着变——**你不需要自己写提示词**。

**显式任务优先。** 工具带一个 `task` 参数（enum 就是当前启用的任务 id）。主智能体选了它，
插件就把 `[task: <id>]` 追加到子智能体开场指令的**末尾**，路由因此**确定性命中**：
不调分类器、零 token、100% 稳定。没选时才走关键词 → 语义分类。

> 为什么在末尾：真实会话里，**前置**标记变成了子会话的侧栏标题（"[task: web-search] 你必须加载 web"）。
> 标题取自首条消息的开头，而 `matchDeterministic` 是全文扫描，所以放末尾零成本且标题干净。

> 已验证（真实 `ToolRuntime`，非文档推断）：作用域自有注册会遮蔽继承的同名工具；
> 祖先作用域注册的名字可以被 `restrict()` 屏蔽；disposer 能精确还原；
> 手写的 JSON Schema 定义被 `register()` 接受，`task` 的 enum 原样进入模型可见的 schema。

> **反向的一半同样是实测结论**：作用域**自有层**注册的名字屏蔽不掉（`restrict` 报
> "unknown global tool"，并且会让整个过滤器失效）。子会话跑的是父预设的副本，那份副本把委派工具
> 装进了子会话自己的层——这就是为什么"屏蔽"不是递归的真正防线，`ctx.subagents` 上的深度守卫才是
> （见上一节与 4.5 的套娃表）。

### 4.5.1 注入的策略文本（通用、可执行、不特化）

策略写在**两个工具的描述**里，由配置自动生成，你不需要自己写提示词。文本刻意保持**通用**：
它讲的是任何工作都成立的委派规则，从不拿某个领域举例——用例子教的规则只会在那个例子上生效。
四个要点，缺一不可：

| 要点 | 文本怎么说的 |
| --- | --- |
| **一体一闭包** | "one child, one closed task"：自足、可独立验收、一次做得完；**绝不把不相关的工作塞进同一个委派**，那会让子智能体哪件都做不好 |
| **各守其位** | 子智能体只在自己的任务内活动；不把主智能体的协调工作丢给它，也不在它干活时自己重做一遍 |
| **说明必须自足** | 子智能体看不到主对话：目标、已与用户确定的约束、交付物、验收标准都要写清；写明你期望回来的接口/格式能消掉大部分返工 |
| **归属不转移** | 拿到任务的子智能体**一直拥有它**：交付后主智能体自己验收，把修改意见或下一步用 `subagent_message` 发回**同一个**子智能体——不要为一次修订/后续步骤/同任务的下一步另开一个子智能体。只有确实是另一个闭包任务时才新开 |

最后一条是这次新增的**能力**而非仅文本：DSH 自带等价的 `send_message`，但它只在预设挂了对应行时存在。
预设没挂 → 主智能体根本无法"继续同一个子智能体"，而策略却要求它这么做，那就是一句做不到的承诺。
所以插件**自己提供两个工具**：

| 工具 | 作用 | 机制 |
| --- | --- | --- |
| `subagent` | 派一个闭包任务 | `subagents.startContinuable({provider:'spawn', label, request})` → 返回 `childId`（**可持续**子会话，交付后仍存活） |
| `subagent_message` | 把修改意见/下一步发回**同一个**子智能体 | `subagents.sendMessage(parent, childId, [{type:'text',text}], {signal})` |

**回归保护**：若当前 DSH 的 spawn 后端没有 `prepareContinuable` 能力，插件**不会**注册
`subagent_message`，并且**改掉策略文本**——改成"每次委派都是一个新的子智能体，交付即结束"，
绝不承诺做不到的事。两条路径都有断言（`test-router-host.mjs` 18c/18e/18f）。

## 4.1 判定细则（回答"何时调用、准不准、会不会缺席"）

**什么时候会问分类器？** 只有前两条规则都没命中时。顺序是固定的：

1. 消息里有 `[task: 任务id]` → 直接用
2. 任务配置的关键词出现在最近对话文本里 → 用它
3. 前两条都没命中 **且** 分类器已启用 → 调一次分类器
4. 分类器没给出候选内的答案 / 未启用 / 失败 → 默认任务
5. 没有可用默认任务 → 保持继承的模型

**「每轮最多调用一次」是什么意思？** 一轮对话里可能有多个 step（模型调一次工具就是一个 step）。
分类结果按 `(会话, 轮次)` 缓存，同一轮的后续 step 复用第一次的结果。
所以一次工具调用**不会**让子智能体中途换模型——轮内是稳定的。

**需要的时候会缺席吗？** 会，而且这是设计的一部分：

| 缺席原因 | 后果 |
| --- | --- |
| 分类器未启用 | 直接落到默认任务 |
| 分类模型超时 / 限流 / 报错 | 直接落到默认任务，并打一行日志 |
| 分类器答了候选之外的词 | 当作没答，落到默认任务 |

**缺席只会退化成默认，不会让这一轮失败。** 路由是增强，不是前置条件。

**怎么保证它按规则走、不抢主智能体的活？** 三条硬约束：

- 主智能体的 `agent/request` 在**第一道判断**就被放行（`isSubagent !== true` 直接返回），
  它连消息扫描都不会发生；
- 分类器是一次**普通嵌套调用**（走 `llm.stream`，不是 `agent/request`），
  所以结构上不可能递归回路由；
- 分类器的路由是显式配置的，别的机制动不了它。

**子智能体由谁决定要不要派生？** 主智能体自己。本插件**不改变**主智能体的工具表、
不注入提示段、不干预它的决策——只在子智能体已经存在之后，决定那个子会话用哪个模型。

## 4.9 这一页永远不会空白（UI 崩溃防护）

设置页曾经**两次**渲染成空白面板：左侧导航有「任务路由」，右边什么都没有，屏幕上没有任何
线索说明是哪个插件出的问题——这是最难排查的一类故障。现在有四道结构性防线：

| 防线 | 防的是什么 |
| --- | --- |
| **faces 解析永不抛** | `inject()` 在**注册 section 时**执行，任何一次抛错就等于整块面板消失。解析失败转成 `fault` 字符串，页面照样渲染并把原因写出来 |
| **`ctx.get('remote.<ns>')` 优先** | `ctx.remote.agentPresets` 不是普通属性，而是名为 `remote.agentPresets` 的**服务**；未声明时读属性会抛 "cannot get property … without inject"。这正是上一次白屏的根因 |
| **镜像读取是全函数** | `useSyncExternalStore` 在渲染期调用 `getSnapshot`/`subscribe`，抛错就是白屏。两个读取都包了 try/catch，失败时返回"未同步"快照，并在页面上显示原因 |
| **错误边界** | 兜住任何其它渲染期异常，显示卡片而不是空白。边界类是**首次使用时才创建**的——模块作用域里 `extends React.Component` 会在 React 不完整时让整个 bundle 加载失败（`test-package.mjs` 抓到的真 bug） |

回归测试专门构造敌意环境：remote 的每次属性访问都抛错、`settingsScope.bind` 抛错、
`getSnapshot` 抛错、`subscribe` 抛错、预设清单拒绝或抛错——**每一种都必须渲染出带标题的页面**
（`test-render.mjs` 的"never a blank panel"一组断言）。

## 4.10 坏掉时能被看见、能被关掉（健康面 + 自动停用）

要求是两句话：**插件坏了要能在设置界面看见报错，并且我要能把它关掉。**

**健康面。** Host 半边暴露**唯一一个**方法 `GET /api/dsh-model-router/health`
（动态插件模式下同时用 `harness.handle('health')`）。只留一个的理由：页面需要的**数据**全部走
Typert Remote 面（`remote.session.modelCatalog`、`remote.agentPresets`），而**运行期状态**不是设置——
写进 settings 命名空间会持久化噪音并且每次都触发 watcher。所以这条通道只承载诊断：

```jsonc
{
  "routing":     { "enabled": true, "tasks": 3, "defaultTaskId": "general", "stats": { … } },
  "delegation":  { "tool": "subagent", "provider": "spawn", "installed": 2, "applied": 2,
                   "service": true, "childDelegation": false,
                   "agents": [ { "id": "…", "preset": "cordis", "granted": true,
                                 "owned": true, "kind": "delegation",
                                 "applied": true, "error": null } ] },
  "capabilities":{ "settings": true, "llm": true, "timer": true, "agents": true,
                   "subagents": true, "agentPresets": true, "webServer": true },
  "errors":      [ { "at": 1789…, "where": "agent/request", "message": "…",
                     "counted": true } ],                                        // 最近 12 条
  "breaker":     { "tripped": false, "reason": "", "consecutive": 0, "threshold": 5 },
  "providers":   { "b-ai": { "failures": 4, "lastAt": 1789… } }
}
```

**`errors[]` 里两种条目：计数与不计数（`counted`）。** 熔断的语义是"插件坏到不能待在请求路径里"，
所以它只数**请求路径**上的失败（`agent/request`）。安装失败、`resolveModelInfo` 查询失败、子过滤器被
拒、屏蔽被拒、配置解析问题，都是**降级**：页面照样显示（`counted: false`），但不会把路由摘出去。
这条区分是实测逼出来的——守卫装不上时每次保存设置会写 2 条，**3 次保存就凑满阈值 5**，把路由整整
停 60 秒；一个配置问题不该造成停摆。

**`delegation` 为什么是三个数而不是一个"装了几个"**（这是被真实故障逼出来的）：

| 字段 | 含义 | 单独看它会误判成什么 |
| --- | --- | --- |
| `installed` | 已经登记、由本插件持有的 fiber 数（**创建即计数**，不等启动） | 0 可能是"没有会话"，也可能是"服务没找到" |
| `applied` | 其中**启动体真的跑过**的数量 | 小于 `installed` 就是"挂了但没起来"（服务在作用域里迟迟不可用） |
| `service` | 本插件作用域里是否看得到 `subagents.start` | false 时根本不会尝试安装，与 fiber 生命周期无关 |
| `agents[].error` | 该 agent 那次启动抛出的原因 | 启动是**延迟**执行的，调用方 try/catch 看不到，只能记在这里 |

设置页把前两个数并排显示成「委派工具已生效 N / 已挂载 M 个会话」：只有相等才代表接管真的生效。

**为什么"接口没回应"本身就是诊断。** Client 半边是**独立的 bundle**：Host 半边挂载失败时，
页面照样渲染（设置页由 Client 半边注册），于是 `404 / 连接失败 / 无 fetch` 会被显示成
「Host 半边可能没有挂载或已崩溃」。这是进程内上报**永远做不到**的那一种故障。

**自动停用（熔断）。** `route()` 里的异常会被计数：连续 5 次失败就把插件**从请求路径里摘出去**
（此后 `route()` 直接返回 undefined，会话保持自己继承的模型——路由是优化，不路由永远能用），
并在页面上写明原因。60 秒后自动重试；**改动任意设置会立即重置**（改配置是人类决定再试一次）。

**能力探测 = 版本适应性。** `capabilities` 记录这次挂载实际找到了哪些服务。DSH 升级把某个服务
改名或移除时，它立刻在页面上显示为"缺失并已降级"，而不是变成一堆看不懂的报错：
委派工具的安装依赖 `agents`/`subagents`/`tools`，缺任何一个就只做路由、不碰工具表；
`webServer` 缺失只是没有健康面，路由照常。

**手动关闭（三级，任何一级都独立可用）：**

| 级别 | 做法 | 适用 |
| --- | --- | --- |
| 1 | 设置页 → 运行状态 → 「停用本插件」（就是总开关） | 页面能用时 |
| 2 | `%DSH_HOME%\profiles\web\cordis.patch.yml` 里给 `dsh-model-router` 行加 `disabled: true`，重启 `dsh web` | 设置页打不开、或需要彻底隔离时 |
| 3 | 什么都不做，等熔断 | 插件自己出错时 |

**第 2 级不会碰到任何预设文件、也不会碰 settings.yaml 里的业务配置**——它只关掉插件自己那一行，
所以"关掉"和"重新打开"都是无损的。三种方式都不会改写任何 agent 预设：
本插件的委派工具是**运行时**装在 agent 作用域里的，fiber 一销毁就干干净净地还原。

## 5. 安装

### 5.1 立刻生效（动态插件，重启即失）

```powershell
node build-router.mjs        # 生成 dsh-model-router.dynamic.json
```

把该文件里的 `host` 与 `client` 分别作为 `code.host` / `code.client` 传给 `cordis_define`，
再 `cordis_run`。客户端 UI 需要你点一次批准。

### 5.2 持久生效（安装为一个包，推荐）

**这是唯一能让设置页也自动加载的方式。** profile 的一行只挂载它点名的那个模块；
浏览器永远看不到它，所以「裸文件行」会挂上 Host 半边却**不产生任何设置页**——
这正是 `name: ./xxx.mjs` 那种写法失败的原因。

`packages/client/modules` 决定什么能进浏览器：它从一行的模块 URL 往上找到最近的
`package.json`，读 `dsh.client` 声明；没有声明的包被跳过，声明了却没有
`exports["./client"]` 的包直接报错。所以持久安装的单位是**包**，不是文件：

```
package/                                    ← node build-router.mjs 生成
  package.json        dsh.bundle + dsh.client + exports
  cordis.patch.yml    包自己的 insert 行（bundle 层）
  lib/index.cjs       Host 半边（Cordis 行）
  lib/client.cjs      浏览器包（window.__ModuleLoader__ 包装）
```

`node build-router.mjs` 会构建、把包 **junction 链接**到
`$DSH_HOME/profiles/web/node_modules/dsh-model-router`，并重写 profile 的
`cordis.patch.yml`。之后**重启 `dsh web`** 即可。

为什么用 junction 而不是 `pnpm add`：链接就是 `file:` 依赖产生的东西，而且重建时
立即刷新——改源码 → `node build-router.mjs` → 重启，不需要重装。

> ⚠️ **不要同时开两份。** 动态插件与 profile 行都会注册 `model-routing` 命名空间，
> 同一个进程里第二份注册会直接失败。要么用动态插件（临场调试），要么用这个包（长期）。

### 5.2.1 激活模型：左下角「Cordis Plugin」到底代表什么

**它只代表「本会话临时挂载的动态插件」，不代表插件是否可用。**

| | 动态插件（Cordis Plugin 面板） | profile 行（推荐） |
| --- | --- | --- |
| 谁挂载 | 你在会话里 `cordis_run` | `dsh web` 启动时按 `cordis.patch.yml` 自动挂载 |
| 生命周期 | 进程内，**重启即失** | 每次启动自动加载，持久 |
| 出现在左下角面板 | ✅ 会 | ❌ **不会**（那不是它的机制） |
| 需要重启 | 不需要，立即生效 | 需要（加载器只在启动时 import） |
| 改设置页有效吗 | 有效 | 有效 |

由此回答三个常见疑问：

- **其他插件为什么不需要这个东西？** 因为它们全都以包 + profile/bundle 层的形式在启动时挂载，
  面板里本来就不显示。面板是「临时插件」的专用视图，不是「已装插件」清单。
- **重启后只改设置界面为什么没用？** 重启会清掉动态插件，此时进程里没有任何路由代码在跑。
  配置（`settings.yaml` 的 `model-routing:` 段）还在，但**没有消费者**。
- **怎么让路由真正生效？** 三件事缺一不可：

```
① 代码在跑：包已随 profile 加载（重启 dsh web 后自动）
② 总开关：   设置 → 任务路由 → 启用任务路由
③ 授权：     设置 → 任务路由 → 按预设授权 → 勾选 diy / diy-smart
```

设置页顶部的状态徽章会直接告诉你「生效中」还是「未生效」，未生效时还会说明原因
（总开关未开 / 还没有授权任何预设），不必去猜。

## 5.2.2 只有包/profile 路径才会遇到的四个坑（已修，记在这里省得再踩）

**(a) 裸文件行没有 client 半边。**
见上：行必须点名一个声明了 `dsh.client` 的**包**，否则 Host 半边挂上了，
设置页却永远不会出现。

**(b) `apply()` 不能返回普通对象 —— 否则整个 profile 树都起不来。**
Cordis 把 `apply` 的返回值当作插件的 effect，只接受 disposer / Promise / 迭代器 /
null-undefined。返回一个诊断对象会得到：

```
Error: dsh: plugin tree failed to load: failed to apply loader entry dsh-model-router: Invalid effect
```

整个 `dsh web` 直接起不来。**动态 runner 容忍这个返回值，所以它只在 profile 路径上炸**——
这正是为什么离线测试必须显式断言 `apply` 返回 undefined。

**(c) client 半边不能在模块顶层读注入的内建量。**
`ctx` / `host` / `styles` / `React` 是求值体的参数，只有 `apply()` 跑起来才存在。
在顶层写 `const E = React.createElement`，浏览器模块加载器一调用 factory 就抛
`ReferenceError: React is not defined`。改成函数包装
（`function E(...) { return React.createElement(...) }`）即可。
动态 client 半边同样会中招，只是之前没走到那一步。

**(d) `ctx.plugin()` 返回的 fiber，`apply` 还没跑 —— 绝不能拿"apply 跑没跑"当返回值条件。**

这是唯一一个**只在真实进程里出现、离线全绿也照样中**的坑，代价是"接管悄悄失效"：

```js
let built = false
const fiber = agent.ctx.plugin({ inject: ['tools'], apply(ctx) { …; built = true } })
return built ? fiber : undefined          // ← 永远是 undefined
```

Cordis **异步**启动插件（`fiber.md`：启动体可以是 async），所以 `ctx.plugin()` 返回时
`apply` 尚未执行，`built` 必然是 `false`。后果不是"没装上"，而是更糟的**装上了却没被记住**：

- 工具确实注册进了 agent 作用域，模型真的在用它 → 路由看起来"有时生效"；
- 但 `delegationFibers` 里没有它 → `/health` 报 `installed: 0, owned: false`；
- **没有任何句柄能撤销它**：撤授权、关插件、force 重建都dispose 不掉这个 fiber，
  于是"撤销即还原"的承诺当场作废，重建还会在同一作用域叠出第二份注册。

修法：fiber **一创建就登记**，另用 `applied` 记录启动是否真的跑过；启动期抛错在
**apply 内部**上报（调用方的 try/catch 根本看不到延迟抛出的异常），并在重抛前先 teardown，
保证"半个安装"不会残留。`/health` 现在同时给出 `installed`、`applied`、`service` 三个数，
把三种"没接管"的原因分开：服务不在作用域里 / fiber 在但启动没跑 / 启动跑了但抛错
（错误进 `errors[]`，`where: delegation startup`）。

> 复现这件事的教训写进了测试替身：`fakeAgent` 现在**也延迟**启动（`queueMicrotask`，
> 还可以用 `startupGate` 把启动挂在半空），于是"同步假设"在离线套件里就会红，
> 而不是等到真实会话里变成一个查不出来的 `installed: 0`。

### 5.3 为什么有构建步骤

同一份路由策略要在三种模块规则下运行：

| 目标 | 模块规则 |
| --- | --- |
| Node 测试 | 普通 ESM，`import` 可用 |
| profile 行 | Cordis 加载器 `import`，静态 ESM 可用 |
| 动态插件 | Host 沙箱用 `new Function` 在 `node:vm` 里求值：静态 `import` 是语法错误、`require` 被 trap、**`import()` 报 "A dynamic import callback was not specified"** —— 完全没有模块图 |

所以策略只写一份（`model-routing-config.js`），由 `build-router.mjs` 拼装产物。
构建只做**去 `export` + 内联依赖 + 拼接**，不转译 —— 发出去的就是审过的代码。
构建还会拒绝任何带 `import` 的 adapter，避免只在运行时才炸。

**依赖内联**：插件需要给 `settings.register` 传一个 schemastery schema
（settings 服务是靠**调用** schema 来解析命名空间的），而 schemastery 及其唯一依赖
cosmokit 本身就是自包含 ESM 文件，所以两者被整体内联，产物零依赖。
`export { mapValues as valueMap }` 这类**别名导出**会被显式回填
（`const valueMap = mapValues`）—— 别名只是导出名，并不会在作用域里创建绑定。

**动态插件的引导加载**：内联后插件体约 87KB，不可能每次编辑都手工粘贴。
所以构建额外产出 `dsh-model-router.plugin-body.js`（去掉 `export`），
动态插件只需几行引导：用已授权的 `fs` 服务读该文件 → `new Function` 编译 → 挂载。
跑的就是审过的源码本身，而不是它的转录。

> 注意：动态插件行需要 `inject` 里额外带 `fs`；profile 行不需要（它是真模块，直接 `import`）。

## 8. 注意事项

1. **只能路由到已注册的路由。** 池里 provider 必须真的挂了适配器
   （`openrouter` / `google` / `b-ai` 都来自 `llm-pi-ai` 的 `settings.yaml` 段）。
   全部不可用时放行原路由，不会把请求打挂。
2. **`reasoningEffort` 会跟着路由走，而且是"就近映射"，不是原样照抄。** DSH 拒绝夹取
   （"no clamping or aliasing is performed"），模型没有的档位会抛 `UNSUPPORTED_REASONING_EFFORT`；
   任务声明的强度会落到目标模型**支持的最近一档**（沿 `max→high→medium→low→off` 向下），低于
   模型底线就取它的最低档，完全不支持推理才不发该字段。
3. **均衡的是负载，不是质量。** 同一个池里的模型质量应当接近，
   否则输出质量会随轮次抖动。免费档（`openrouter/free`）更适合放搜索/轻量池。
4. **默认不路由任何预设。** 装完插件，一切照旧；必须去设置页显式授权某个预设。
5. **每轮一次额外调用。** 只有第 3 级被走到时才发生，且每轮最多一次；
   把分类模型设成一个便宜/免费的模型即可。

## 8.1 两个只有动态插件才会遇到的坑（已修，记在这里省得再踩）

**(a) `settings.register` 要的是 schema，不是形状对象。**
settings 服务靠**调用** schema 解析命名空间（`index.ts:748` 的 `schema(merged)`），
所以第二个参数必须是可调用的 schemastery schema。传 `{ type: 'object' }` 会得到
`schema is not a function`。

**(b) `settings.replace` 的 plain-object 检查是「跨 realm」比较。**
`isPlainObject` 判定 `Object.getPrototypeOf(value) === Object.prototype`。
插件跑在 `node:vm` 沙箱里，沙箱的 `Object.prototype` 与宿主的是**不同对象**，
于是沙箱里造的普通 `{}` 会被宿主侧拒绝：
`settings replace for "model-routing" must be a plain object` —— 而在这里看它明明是 plain 的。

实测四种构造，**只有 null-prototype 通过**：

| 构造 | 是否被接受 |
| --- | --- |
| `{ … }` 字面量 | ✗ |
| `JSON.parse(...)` 往返 | ✗ |
| `{ ...spread }` | ✗ |
| `Object.create(null)` 赋值 | ✓ |

因为 `proto === null` 在任何 realm 下都成立。所以适配器写入前统一过一层
`toHostPlain()`，把整棵树递归重建为 null-prototype；settings 侧随后会用自己的
`cloneJsonShaped` 把数据重建成宿主对象，null 原型不会外泄
（`mergeLayers` 也是 `{ ...under }` 重新铺开）。
回归测试 `assertRealmSafe` 会在离线阶段拦住退回成普通对象。

## 8.2 双语与可移植性：两条"靠自觉就一定会漏"的规则，改成测试来管

**界面双语（跟随 DSH 语言）。** 设置页用内置插件同一套机制：`ctx.locale.register(NS, { zh, en })`
注册字典、`ctx.locale.bind(NS)` 取当前语言、订阅 `ctx.locale` 的重渲染让切换立即生效。
三条规则交给测试，而不是交给记性：

- **中文只能出现在字典与注释里**——测试读客户端源码，把 `const COPY = {…}` 区块与注释行剔除后，
  断言不再有任何中日韩字符。这条抓过 107 行：部分替换完成后，页面在英文下仍会显示中文。
- **两种语言的键集合必须一致**——少一个键就是某个语言下会出现 `undefined`。
- **渲染级验证是决定性的那条**：测试用真实 React 渲染两次（en 与 zh），断言英文渲染里**一个中文字符
  都没有**、且两次输出确实不同。源码扫描替代不了它——把 `COPY.zh[...]` 写死 69 处那种错误，只有
  渲染出来才看得见。

**README 双语（`README.md` 英文 / `README.zh.md` 中文）。** 机器无法评判文笔，但能评判"两种语言说的是
不是同一件事"：`test-docs.mjs` 比较**章节数、围栏代码块、表格行数、内联代码 token 集合**，以及两边
都必须出现的**配置键与命令**。漏一节、少一条命令、只更新一种语言，测试立刻红。

**可移植性：四个"只在这一台机器上对"的真实缺陷，和一条机器可查的规则。** 全部来自实测：

| 缺陷 | 后果 | 现在 |
| --- | --- | --- |
| 构建给 `symlink()` 传了 Windows 专有的目录链接类型 | POSIX 报 EINVAL，**非 Windows 机器根本构建不了** | 按平台选择 |
| `test-store.mjs` 里硬编码的盘符兜底路径 | 只在写它的那台机器上正确 | 统一用 `DSH_HOME`，否则用户主目录 |
| 两个套件把临时目录写到系统 temp | Windows 上通常落在 C 盘，失败时还留垃圾 | 仓库内 `.tmp/`，跑完即清 |
| 产物 banner 嵌了本机 `node_modules` 绝对路径 | 机器路径进了要分发的产物 | banner 只写包名与文件 |

`test-portability.mjs` 把"不得有绝对路径 / 不得写系统临时目录 / 不得出现平台专有的 symlink 类型 /
PowerShell 只能出现在测试入口"变成断言，**并连生成产物一起扫**——产物才是真正被加载的东西。

> 还有一条教训不属于代码：**子进程不得碰版本控制**。一次 `git reset` 把尚未提交的改动整批清掉了
> （构建修复、CHANGELOG、英文 README…），而它们当时已经通过验证。现在委派任务的硬规则里明确禁止
> 在仓库里执行任何 git 命令。

### 8.3 一轮钉住一个模型：设计如此，但它会把额度集中到一轮里

第 4 级阶梯里有一条刻意的设计：**同一轮（session × turn）内不再重新选模型**，即使中途撞上失败。
理由是 prompt 前缀缓存——每步换模型就意味着整段上下文按非缓存价重算，省下的均衡收益远小于
丢掉缓存的代价。代价则在后来被一次真实的额度调查翻了出来：

| 事实 | 数值 |
| --- | --- |
| 一个委派子会话的**第 1 轮**步数 | **438**（其中 431 步在同一个模型上） |
| 该轮在 `qwen3.7-flash` 上的消耗 | **66.9M**（cacheRead 63.1M，为总额的 94%） |
| 全部署该模型消耗 | 66,965,270 → **这一轮占 99.3%** |
| 其余 9 个会话合计 | 约 0.48M（分类器 + 探测子会话） |

机制是三件事叠在一起：**委派时没写 `task`**（于是分类器挑了一个池）、池的全局加权轮询**正好轮到
qwen**（此前 google 因 429 配额被跳过）、以及**一轮钉住**把后面 431 步全部留在它身上。每步重发约
146k token 的上下文，所以消耗由 cacheRead 主导——缓存读单价低，但**在配额口径下照样计数**。

三条可执行结论（未改代码，先记为设计取舍）：

1. **跨轮冷却**：本轮因 429/欠费被跳过的 provider，目前只影响本轮；下一轮它会被重新发牌。加一个
   跨轮、带过期的冷却表就能让那个子会话从一开始就拿到别的模型。
2. **长轮重估**：步数或上下文超过阈值后重新选一次模型，可给单模型暴露量封顶——代价是丢掉这段缓存。
3. **委派侧**：把"大体量机械改写"交给一个 `bulk` 式任务（低推理档 + 便宜池）并显式写明 `task`，
   比让它走通用池划算得多——这正是默认样本里 `bulk` 存在的理由。

`session-usage.mjs` 就是这次调查留下的工具：会话日志里每条 `assistant/message` 都带 `usage` 和产生它的
模型，所以"额度去哪了"可以逐会话、逐轮、逐模型算清楚。它也算不出**分类器**——分类器是嵌套调用、不落
会话日志；但它有明确上界（每次至多 `maxInputTokens` 输入、几百输出、一轮至多两次），除非死循环，
否则不可能是主因。
